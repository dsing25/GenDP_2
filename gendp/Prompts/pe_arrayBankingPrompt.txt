# Architecture overview
The first thing is that we've been cheating the line width. Line width is 64, so when we do a mvd
from the pe to SPM we have been loading addr and addr+1, but really we need to load (addr>>1) and
(addr>>1)+1. This change needs to be made within the pes. If a mvdq loads both, then we load both.
If it's just a single load, then we use the last bit of the load address to determine which of the
two data elements to use TODO this will involve some changes to simulator code.
If it is ever a doubledata and the address %2 != 0, then we need to throw an error. Double loads
must always be aligned.

This is the system we are trying to model. For illustration, assume just two ports, but in reality 
we will have one for each bank, so 8 for SPM and 4 for S2


SPM:
====================================================================
+ b1 //buffer for port1 which corresponds to first bank
+ b2 //buffer for port2 which corresponds to second bank

S2:
====================================================================
+ b1 //buffer for port1 which corresponds to first bank
+ b2 //buffer for port2 which corresponds to second bank

These buffers are implemented as queues.

S2_WRITE_LATENCY = 3
S2_READ_LATENCY = 2*S2_WRITE_LATENCY

Illustration, a single mv instruction comes in going from SPMAddr to S2Addr. S2Addr is sorted
according to the bank it needs to go to, and is placed in that buffer, say S2.b1. SPMAddr is sorted 
according to the SPM bank it needs to go to, and is placed in that bank, say SPM.b1. For the S2 this
is easy. We use a linewidth of 64, i.e. 2 ints, and our memories are int addressable, so the S2 bank
is (S2Addr >> 1) % NUM_BANKS. For the SPM, it is more complicated. Read the SPM to see how it is
indexed. High order bits determine the bank group, and the low order bits determine the bank within
the bank group. Essentially (SPMAddr // BANK_GROUP_SIZE) = BANK_GROUP_INDEX and (SPMAddr >> 1) % 2
gives the bank index within the BANK_GROUP. 

### cycle 0
We write into the buffers so that
These buffers have the following attributes:
| address | data1 (init -42) | data2 | ready1 (bool init true for read, false for write) | ready 2 (same) | rd/write (enum) | src/dst (enum. currently SPM or S2) | src/dst addr | singleData |

As with  SPM accesses, they can be single or double loads because we load in lines of 64.

in S2.b1
| S2Addr | -42 | -42 | true | true |read | SPM | SPMAddr| true |
in SPM.b1, we look at the destination address %2 which gives us the data we're going to use, so
SPMAddr % 2, in this case lets say that is 0, so ready1 is false, and ready2 is true. You may choose
to use arrays for these elements instead of data1/2 and ready1/d
| SPMAddr| -42 | -42 | false| true | write| S2  | S2Addr | true |


###cycle 1

S2 can issue up to four requests per cycle, one from each queue. We have a rotating priority which
starts at b1, and then goes to b2 and back to b1. b1 has something in it and it is ready, so we
access the S2 at that data location. This will work similar to the way the SPM access works right
now. The S2 class will have some internal storage which keeps a count of cycles until ready, and the
class will be tickable. Every cycle we tick and decrement the count. When something is ready, it
will go to it's dest.
So we issue the read, and the line entry in b1 is sent into the S2 with a timer equal to 
S2_READ_LATENCY-1. Data is read from (S2Addr>>1) (two ints) and placed in the data field. We read 
from shifted 1 because of the line address. The line entry in b1 is 
then cleared.
Importantly, S2 can be pipelined. Where S1 has only one slot per bank, and while that slot is busy,
we cannot put another request there, the S2 can have up to S2_READ_LATENCY requests per bank.
Although it should be enforced that no two writes in the same bank have the same cycles_remaining,
and no two reads in the same bank have the same cycles remaining.

Meanwhile, S1 has the same rotating priority. It sees that b1 has something in it, it checks to make
sure that the SPM is not already using the b1 port, i.e. there is not an outstanding request to the
scratchpad which uses bank1. These two conditions are met, but the ready bit of the buffer entry is
false, so we do not write. The priority is incremented.

###cycle 2
same checks are performed, but there is nothing in s2, so no further action. The entry we inserted
gets it's cycles_remianing decremented.
cycles_remaining=S2_READ_LATENCY-2

###cycle 3
cycles_remaining=S2_READ_LATENCY-3

###cycle 4
cycles_remaining=S2_READ_LATENCY-4

###cycle 5
cycles_remaining=S2_READ_LATENCY-5

###cycle 6
cycles_remaining=S2_READ_LATENCY-6 == 0
the S2 entry has no more cycles remaining, so in the tick function, it checks the dst, sees that it
is SPM, goes to SPM and checks the src address of every read entry that has S2 as src. 
It will really be checking (srcAddr >>1) for single loads because this gives the line address. 
For double loads we need to check (srcAddr >> 1) and (srcAddr+1 >> 1). See the compl,icated cases
below.
If it matches then the data we are carrying
applies here. Now that we have a match, we set SPM.b1.entry.data[address%2] = data[srcAddr %2].
Note the srcAddr final bit determines which piece of the read data we use, and the final bit of the
address gives the index of the data field in the entry we are going to write to. If it was not a
sinlgeData then we would write both entries into the data.
Once we've written the data we clear the s2 entry

Now we check for S2 anything in the buffers. See nothing.

We check S1 buffers, see that there is a ready store, and attempt to issue the store. If there was
already an entry in SPM there, then the pes are already using that slot, so we'll need to wait, but
if there is not, then we can issue into the slot. 

Note that because it was a singleData we will only write the data[0] to the appropriate address,
which may not be the first in the line.

This example should clarify the role of the buffers and the overall control flow. A couple points as
things get more complicated.

### What about many stores in a buffer?
If there are many stores in the SPM, then you may not bypass a store. the store below has to wait
for the first store to issue. This will not cause any deadlock because whenever I issue a store I
allocate slots in both buffers simultaneously. Before allocating slots for any other instructions.
This avoids situations where s1 is blocking ld2 in S2 and s2 is blocking ld1 in S1 for example 

### What about stores and reads in same buffer?
There can be both stores and reads in the same buffer. No preference is given for loads over stores.

### How do we handle mvdq (move double quad) instruction?
A mvdq places 4 loads and 4 stores in the src and dst buffers according to their bank indices. Each
load/store is a double load/store. The trick is when we have misaligned addresses. If you are doing
a mvdq from addr 1 say to addr 0 in spm. You will issue 5 reads actually:
singleData 1
doubleData 2
doubleData 4
doubleData 6
singleData 8

Note there will only be 4 writes in the SPM however, they will be doubleData stores with odd src
addrs. because of this they will match two different loads. Each load will match the srcAddr >> 1 of
one load and the (srcAddr >> 1) + 1 for the other load.

This is a complicated edge case. Please think very deeply about how to handle these and make sure it
doesn't break anything. Ask many questions if you're confused.

### How large are the buffers?
To start, infinitely big. Later we'll size them to be 8.

### What if we use up the buffer size?
The pe_array will immediately stall. If in the middle of a mvdq, none of the loads/stores will be
issued.

### Is it symetric for S2<-SPM?
Yes! The only difference is what happens when a entry in the buffer is freed, i.e. does it go to the
SPM outstanding requests, or does it go to S2 outstandingRequests which have more entries because
they are pipeleined. Otherwise, it should be the same going to S2 coming from S1.
