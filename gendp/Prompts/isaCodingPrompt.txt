## Hints For coding in gendp isa
**It is absolutely essential that you always keep these in your context window. If you run out of
context, compress other things and reload the hints.**
+ Gendp ISA is very verbose and it is easy to make mistakes. Be very careful and run checks whenever
  possible.
+ You'll note that in wfa_instruction_generator I have an inline function `write_block_code`. You
  should make similar functions for `loadSpmRegMapped` and `storeSpmToWavefrontStrided`. These
  should be the only functions you make.
+ Do not use variables or complex control. For small loops, like over num_pes I use for loops, and
  I very sparingly use functions. These are fine and make the code more readable, but understand
  that when you create a for loop, you are not looping in the code, you are duplicating the
  instruction for each iteration of the loop. The loop will essentially be unrolled in the code.
  Therefore use this very sparingly to minimize instruction footprint
+ You cannot use variables. It is essential that you do not use variables. If you use variables your
  code will be worthless. You may use the loop counter if doing a for loop as in the previous point.
  You may also use the arguments of a function, but keep them to a minimum. These will be expanded
  into constants. You may also use constants enumerated at the top of the file. These in fact should
  be used to improve readability. Other variables cannot be used.
+ There is no multiply unit in the control trace. When I do a multiply in the magic instrucitons, it
  is always with a power of 2, therefore, you can shift by the log. When multiplying by 3, I unroll
  3 additions.
+ Branches in Gendp are very difficult. You should be very careful with them, and always check the
  branches after each step. The issue is that branches jump by a constant offset. That is, they
  cannot jump to a LOOP label as in traditional ISA. Instead they jump a hardcoded value like 9. If
  you add an instruction just below that jump, well now you need to jump 10! So every time you add
  an instruction, check that there are no branches that cross it from above or that jump backwards
  over it from below. If there are, you will need to increment their offsets. If your code does not
  match, the first thing you should check is whether you have broken one of the branches.
+ In many cases, you should be able to move part of a magic instruciton into the instruction
  generator, and remove it from the magic instruction. This way you can test piece by piece instead
  of dumping the entire magic instruction into the simulator
+ When writing spm accesses from the pe, you must stall for 2 cycles to make sure the port is free.
  This is not the case with pe_array. You need not buffer your write/reads. You can have back to
  back read/writes.
